05 — Under the Hood

The engineering that makes it a platform

Decisions a template can't make for you.

Concurrency

Race-condition-safe inventory

Stock decrements run inside database transactions at reservation time. Verified by simulating two simultaneous buyers competing for the last unit — exactly one wins, every time. When an admin updates stock, customers see it immediately.

Architecture

Built for ephemeral infrastructure

All media — payment receipts, QR codes, product photos, blog images — is stored in the database rather than on disk, because the hosting tier's filesystem doesn't persist between deploys. The app survives every redeploy with zero data loss, at zero infrastructure cost.

Data integrity

Self-healing bookkeeping

Every paid order automatically logs its sale as income and its exact shipping cost as an expense. When this feature shipped after real orders already existed, an idempotent boot-time backfill repaired historical records safely — no manual data fixes, no double entries.

Async migration

Sync to distributed SQLite

The entire data layer was migrated from local synchronous SQLite to Turso's async distributed SQLite to go cloud-native — every query path rewritten, verified end to end, with zero frontend changes required.

Dynamic content

Everything is editable

Hero image, featured products, badges, coming-soon cards, brand story, photo stories, payment channels, contact links — all live-editable through the CMS with server-side sanitization on rich content. No developer required, ever.

Input hardening

Defense at both ends

Every money field and user input is validated client-side and server-side — a malformed shipping fee can't silently become free shipping, and rich text can't smuggle scripts.

08 — Challenges

The hard parts

CMS

Building a CMS from zero

Designing an editing experience simple enough for a non-technical owner but powerful enough to run a real business — every affordance had to be invented, not installed.

DATA

Database architecture

Modeling orders, variants, reservations, media, and money movements so that every state change keeps stock and books consistent — including cancellations and reversals.

SYNC

Dynamic inventory

Keeping what customers see truthful under concurrency: reservations, expiries, restocks, and admin edits all mutating the same counts safely.

STATE

State management, no framework

Cart, currency, order lifecycle and UI state handled in disciplined vanilla JavaScript — proving the fundamentals without hiding behind a framework.

MOBILE

Responsive everything

Editorial desktop layouts that collapse into genuinely usable mobile experiences — including rethinking interactions (like the photo strip) rather than just shrinking them.

PROD

Real production constraints

Free-tier hosting with an ephemeral filesystem, cold starts, DNS migration from a locked registrar config, and testing against a live business that was actively selling.

12 — Lessons Learned

What this project made me

Systems thinking

A feature is never just UI — it's data model, state transitions, failure modes, and the bookkeeping consequences of each. I learned to design the whole system before writing the first line.

Business first

The most valuable decisions weren't technical. Launching with manual payment verification instead of waiting for a payment gateway put the business in market months earlier.

Production humility

Deploying to real infrastructure with a live business taught me things tutorials never could: ephemeral disks, DNS propagation, cold starts, migration under load.

Designing for non-engineers

The CMS forced me to think like a UX designer: every workflow had to be obvious to someone who has never seen a database.

Communication is a feature

Documentation, video walkthroughs, and training turned a codebase into a business tool the client actually trusts and uses daily.

Scalability as a habit

Async data layer, API-first routes, additive migrations, idempotent repairs — building patterns that let the platform grow without rewrites.
